# HMCL 维护版：怎样更新、测试和回退

维护分支：`codex/hmcl-maintenance`。源码在这个项目中修改；应用目录只放编译结果。不要直接编辑 JAR，也不要把新 JAR 覆盖到旧文件名上。

## 现在保存了什么

- `hmcl-imported-20261102` 标签保存了本次维护开始前的源码。
- `upstream.json` 登记官方来源和基线提交。导入的目录没有 Git 元数据，因此上游提交仍是未知，不能把它当作官方某次提交。
- 同步功能继续集中在 `AllegianceSync` 和 `AllegianceSyncTask`。原生启动流程在必要文件准备之后调用同步；无法识别版本时提示并跳过同步。
- CurseForge 的搜索、详情、文件查询、版本列表、更新日志、分类和指纹查询共用 `CurseForgeMetadata`，不再各自拼官方请求。
- `manage.py` 负责构建归档、记录实际验收、切换版本。它不负责把未验证版本自动发给玩家。

## 1. 修改源码，提交一个明确版本

以后先确认仍在维护分支上，再改代码。只提交 HMCL 源码和相关维护文件，不需要把外层项目其他尚未完成的改动一起提交。

每次提交写清楚一个实际改变，例如“修复首次导入版本检测”或“更新 Mod 元数据来源”。不要把上游更新和自己的功能修改混成一条提交。

本机外层 Git 的自动整理发现过损坏对象，已写入 upstream.json。维护开始前已成功导出独立源码快照 `HMCL/hmcl源码/HMCL-imported-baseline-20261102.zip`。这次没有修复或删除损坏对象，也不声称外层全部历史完整。后续每个候选都会再次导出并校验自己源码子树的 ZIP。

## 2. 构建一个新候选，不替换当前应用版

在本源码目录打开终端，运行：

```powershell
py -3 maintenance/manage.py build maint-20261102.4
```

如果没有 py，可用本机已经安装的 Python 运行同一脚本。脚本在 Windows 上优先使用 JAVA_HOME；没有设置时尝试本机 JDK 21。

脚本会检查 HMCL 源码已经提交，执行维护脚本测试、同步及 CurseForge 相关自动化测试，然后编译 JAR。构建或测试失败就停止。任何一步失败都会保留记录，不修改应用目录。

每次使用一个没有用过的版本名。成功后文件放在 `HMCL/维护版本/maint-20261102.4/`：

| 文件 | 你用它做什么 |
| --- | --- |
| `preview.cmd` | 打开这个候选；运行数据放在独立的 maintenance-runs 目录 |
| `Allegiance-HMCL-版本名.jar` | 本次编译的启动器 |
| `source.zip` | 从本次源码提交导出的完整源码子树 |
| `release.json` | 源码提交、上游记录、测试范围、产物校验值 |
| `tests.zip` | 自动化测试报告 |
| `build.log`、`script-tests.log` | 构建和维护脚本测试日志 |
| `acceptance.json` | 五项实际验收记录，初始全部待测试 |
| `SHA256SUMS` | 核对文件是否被改动 |

旧版本和失败版本都不会被覆盖。源码提交和源码 ZIP 可追溯；这不承诺在任意机器上构建出逐字节相同的 JAR。

## 3. 先跑一个只读联网探针

```powershell
py -3 maintenance/manage.py probe maint-20261102.4
```

它用候选 JAR 内的真实请求策略，读取一个项目及其指定文件的资料，并记录项目名、文件名、尝试的来源和耗时。默认项目／文件来自此前报 403 的日志。不会读取后台管理密钥，不下载 JAR，不修改游戏目录。

探针通过只代表这两个资料接口当时可用，不代表几百个 Mod 全部能下载，更不代表已经能进服。探针失败会保留结果，不会替换应用版。

## 4. 用候选完成五项实际验收

双击候选目录里的 `preview.cmd`。它使用单独的联调工作区，请在里面导入整合包副本，不要指向常用客户端原件。运行数据与可能包含账号信息的文件在 `HMCL/maintenance-runs/版本名/`，不属于发布归档，不要打包发给别人。

按顺序完成：

1. **全新导入**：从整合包 ZIP 导入一个新实例，不能靠旧实例已经准备好的文件冒充首次导入成功。
2. **补齐依赖**：实际完成 Java、游戏库和整合包必要文件。记录下载失败的文件和来源；未知版本提示不得挡住启动。
3. **同步补丁**：后台发布一个小配置补丁，在测试副本制造可控差异，确认同步生效且旧文件有备份。再次启动不应重复替换同一份已一致文件。
4. **启动进服**：真正进入游戏并连接目标服务器，确认版本兼容与主要功能。
5. **单 Mod 回档**：用可测试的自有 JAR 做一次替换，关闭游戏后从菜单恢复单个旧 JAR，核对其他 Mod 未改变。再次启动仍遵循后台当前生效发布，长期回档要在后台发布对应候选。

每完成一项再记录结果，不要预先全部勾成通过。例如：

```powershell
py -3 maintenance/manage.py record maint-20261102.4 fresh_import passed --tester David --note "实际使用的 ZIP、客户端版本和导入结果"
```

五项记录名依次是 `fresh_import`、`dependency_completion`、`sync_patch`、`launch_and_join`、`single_mod_restore`。失败时把 passed 换成 failed，并写明原因。

只有实际执行过才能写 passed。脚本检查记录完整性，但无法代替人判断游戏是否真的进服。记录包含测试人、说明、时间和具体 JAR 校验值，换了产物需要重新验收。

## 5. 验收通过再切换应用版

先关闭当前启动器与游戏，然后运行：

```powershell
py -3 maintenance/manage.py promote maint-20261102.4
```

脚本会重新校验构建产物和五项验收。缺少任一项就拒绝切换。通过后把这个版本以新文件名放入应用目录，并切换 `start-local-sync.cmd`。旧 JAR、旧 CMD 和切换记录都保留。

要退回以前已经验收过的维护版本，重新 promote 那个版本即可。启动器版本回退和网页里的 Mod 回档是两件事，不要混淆。

## 接口来源现在怎样管理

统一配置为 JVM 参数 `hmcl.curseforge.source`：

- `auto`：没有官方密钥直接使用 MCIM；有密钥先官方，失败再 MCIM。
- `official`：仅用官方，需要自己的 API 密钥。
- `mcim`：仅用 MCIM，官方密钥不会发送过去。

默认是 auto，候选 CMD 也使用 auto。它是 CurseForge 元数据专用配置；Minecraft 和 Java 下载仍使用 HMCL 原有设置。

元数据保留最多 512 条、15 分钟的进程内缓存。已缓存资料在来源暂时失败时可继续使用；失败来源暂停请求 60 秒。404 保留为“文件不存在”，不会伪造成功结果。进程退出后这份内存缓存消失，已解析的整合包清单仍由 HMCL 原有流程保存。

请求不跟随重定向，避免把密钥转发到别处。查询文件会核对项目 ID 和文件 ID。JAR 的实际下载、完整性检查与进度继续使用 HMCL 原生流程；不会因为资料能读到就声称整个整合包下载已验证。

MCIM 是外部服务，可能不可达或调整接入要求。请按其要求登记应用名称与 User-Agent（当前为 Allegiance-HMCL/0.1）；这次没有替你发送登记申请，也没有借用官方 HMCL 的密钥。

## 以后怎样跟进 HMCL 上游更新

首次迁移前先确定一个明确的官方标签或提交，保留它的干净副本，逐项核对当前导入源码已经包含哪些定制。核实之前 upstream_commit 保持 null。

之后把上游更新单独记录到一个升级分支，再移植自己的维护提交。重点检查 LauncherHelper 的同步调用位置、GameInstancePage 的菜单入口、CurseForgeRemoteAddonRepository 的共享请求调用。完成构建和五项验收后再切换应用版。

当前导入快照不是已确认的上游历史，不能直接承诺无冲突 rebase，更不要把下载的最新上游源码直接覆盖到工作目录。上游远程更新、合并及正式验收都不会由这个脚本自动执行。
